# Proposal

## Why

This module has never used a spec-driven workflow: it has no Agent OS directory and no OpenSpec specification. Its behaviour is documented only in `variables.tf` descriptions and the README. The sibling modules (`keycloak`, `vault`, `gitlab-management`) already plan changes through OpenSpec with pinned standards stores. This is the first adoption of OpenSpec here. Recent releases added a Key Manager key for secrets (`secrets[*].key_id`), HSM key protection (`keys[*].protection_level`) and write-only secret data (`secret_versions[*].data_wo`); a baseline contract lets the next change write delta specs against what is released.

## What Changes

- Configure `openspec/config.yaml`: reference the `quality`, `repository` and `terraform` stores pinned to a tag, with module-specific `context`, per-artifact `rules` and `operations` guidance. `CHANGELOG.md` is generated by git-cliff from commit subjects, so the guidance says so instead of asking for a hand-written entry.
- Add `AGENTS.md` (project summary, non-negotiables, module-specific rules, standards lookup, workflow, precedence, commands) and `CLAUDE.md` importing it.
- Install the `openspec-*` skills for Claude Code (`.claude/skills/`) and OpenCode (`.opencode/skills/`).
- Write the baseline capability specs under `openspec/specs/`, describing the module **as released today**, including what lands in state (`secret_versions[*].data`) and what is write-only (`secret_versions[*].data_wo`).
- Tooling: pin the `openspec` CLI and node in `mise.toml`, add `spec-validate` and `spec-setup` tasks, add `scripts/openspec-setup.sh`, validate specs in CI through `.gitlab/specs.yml` (`validate:specs`).
- README "Contributing" points to the spec workflow.
- No change to any `.tf` file, input, output or resource: semver **patch**. There are no unit tests yet (`tests/` does not exist); the first behaviour change adds `tests/main.tftest.hcl`.

## Capabilities

### New Capabilities
- `module-contract`: supported OpenTofu/Terraform and provider versions, no provider/backend blocks, organization/project/region inputs, project resolution and the outputs.
- `secrets`: Secret Manager secrets: name, type, path, protection, tags, ephemeral policy and the optional Key Manager key that encrypts the versions.
- `secret-versions`: secret versions: exactly one of `data` (in state) or `data_wo` (write-only), `data_wo_version`, the 64 KiB limit.
- `encryption-keys`: Key Manager keys: usage and algorithm pairing, protection level, rotation policy, deletion protection.
